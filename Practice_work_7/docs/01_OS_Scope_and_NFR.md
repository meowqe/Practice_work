# Занятие 1. Границы операционной системы и нефункциональные требования

## 1. Название и концепция

**MyOS** — учебная операционная система с монолитным ядром, работающая как программа на Python 3.10+. Физическим носителем служит база SQLite (`db/os.sqlite`): она хранит пользователей, процессы, файлы и журнал системных вызовов. Пользовательские программы (оболочка) обращаются к ядру только через системные вызовы, ядро проверяет права, выполняет операцию и журналирует её.

Основная идея: показать взаимодействие подсистем ОС (процессы, память, файловая система, защита) без работы с реальным железом.

> Акцент индивидуальной темы (планирование / файловая система / память / безопасность) необходимо уточнить и отразить в п. 2–5 при защите.

## 2. Границы системы

### 2.1. Входит в границы (реализуется)

| Подсистема | Что реализуется |
|---|---|
| Ядро и системные вызовы | Диспетчер вызовов, таблица `syscalls.TABLE`, обработка исключений |
| Управление процессами | Таблица `processes`, состояния (created/ready/running/waiting/terminated), очередь планировщика (Round Robin) |
| Управление памятью | Учёт памяти процессов в КБ, лимит на процесс, выделение/освобождение |
| Файловая система на SQLite | Таблица `files`: создание, чтение, запись, удаление, владелец |
| Защита | Логин/пароль (SHA-256), роли `admin`/`user`, проверка прав в ядре |
| Журналирование | Таблица `syscalls_log` + файл `logs/os.log` |
| Командная оболочка | Цикл команд, справка, вызов системных вызовов |

### 2.2. Не входит в границы (имитируется или исключено)

| Функция | Обоснование |
|---|---|
| Работа с реальным оборудованием | Требует ассемблера/режима ядра; Python работает в пользовательском пространстве хост-ОС |
| Прерывания и драйверы | Заменяются заглушками (таймер, клавиатура, диск, экран); реальные драйверы требуют знания аппаратуры |
| Настоящие виртуальная память и страничная трансляция | Выполняется хост-ОС; в MyOS — только учёт объёма памяти |
| Сетевые протоколы | Не относятся к теме и не помещаются в отведённое время |
| Интеграция с каталогами (LDAP/AD) | Избыточна для локальной учебной системы |
| Графический интерфейс | Тема ограничена консольной оболочкой |
| Реальное выполнение исполняемых файлов | Процессы моделируются записями в БД |

## 3. Роли и сценарии использования

**Роли:** *Пользователь* (работа только со своими файлами), *Администратор* (все права, управление пользователями), *Система* (планировщик, сборщик завершённых процессов).

| № | Сценарий | Актор | Последовательность системных вызовов | Модули |
|---|---|---|---|---|
| 1 | Вход в систему | Пользователь | `sys_login(login, password)` → чтение `users`, сравнение SHA-256 → установка текущего пользователя | shell, kernel, syscalls, auth, db |
| 2 | Создание файла | Пользователь | `sys_create(path)` → проверка прав на каталог → INSERT в `files` → запись в `syscalls_log` | shell, kernel, fs, db |
| 3 | Чтение файла | Пользователь | `sys_open(path)` → `sys_read(fd)` → проверка существования и прав → SELECT из `files` | shell, kernel, fs, db |
| 4 | Запись/удаление файла | Пользователь | `sys_open` → `sys_write(fd, data)` / `sys_unlink(path)` → проверка владельца | shell, kernel, fs, db |
| 5 | Запуск процесса | Пользователь | `sys_exec(name)` → проверка прав и лимита процессов → INSERT в `processes` → `sys_alloc` → постановка в очередь планировщика | shell, kernel, proc, mem, scheduler, db |
| 6 | Просмотр процессов | Пользователь | `sys_ps()` → SELECT из `processes` | shell, kernel, proc, db |
| 7 | Завершение процесса | Пользователь/Админ | `sys_kill(pid)` → проверка владельца → `sys_free(pid)` → состояние `terminated` | shell, kernel, proc, mem, db |
| 8 | Выделение памяти | Процесс | `sys_alloc(pid, kb)` → проверка лимита → обновление `processes.memory_kb`; при превышении — отказ и запись в журнал | kernel, mem, db |
| 9 | Просмотр журнала | Администратор | `sys_log_view(n)` → проверка роли `admin` → SELECT из `syscalls_log` | shell, kernel, db |
| 10 | Управление пользователями | Администратор | `sys_useradd(login, pwd, role)` → хэширование → INSERT в `users` | shell, kernel, auth, db |
| 11 | Планирование | Система | `scheduler_tick()` → выбор процесса по Round Robin → смена состояния ready↔running | scheduler, proc, db |
| 12 | Завершение работы ОС | Администратор | `sys_shutdown()` → остановка процессов → закрытие соединения с БД | shell, kernel, db |

Уже реализованы в прототипе: `sys_echo`, `sys_get_users`.

## 4. Нефункциональные требования

### 4.1. Производительность
| ID | Требование | Метрика | Проверка |
|---|---|---|---|
| P1 | Время обработки одного системного вызова | ≤ 50 мс | `time.perf_counter()` в `Kernel.call`; превышение пишется в лог |
| P2 | Одновременно поддерживаемых процессов | ≥ 10 | Тест: запуск 10 `sys_exec`, все в состоянии ready/running |
| P3 | Время старта ОС (boot + init_db) | ≤ 1 с | Замер от запуска до баннера |
| P4 | Квант планировщика | 100 мс, отклонение ≤ 10 % | Замер в тесте планировщика |

### 4.2. Надёжность
| ID | Требование | Метрика | Проверка |
|---|---|---|---|
| R1 | Ошибка в процессе не роняет ядро | 0 аварийных завершений на 100 ошибочных вызовов | Тест с исключениями; процесс → `terminated`, запись в лог |
| R2 | Превышение лимита памяти | Отказ `MemoryError`, лимит 1024 КБ/процесс | Тест `sys_alloc` сверх лимита |
| R3 | Целостность БД | Транзакции: при сбое частичных записей нет | Тест с принудительным исключением между операциями |
| R4 | Неизвестный вызов/команда | Понятное сообщение, ядро продолжает работу | Ручной тест (`foo` в оболочке) |

### 4.3. Безопасность
| ID | Требование | Метрика | Проверка |
|---|---|---|---|
| S1 | Пароли только в виде хэша SHA-256 | 100 % записей `users`, длина хэша 64 | SQL-проверка; тест `test_passwords_hashed` |
| S2 | Пользователь не изменяет файлы администратора | 100 % таких попыток отклонено | Тест прав |
| S3 | Журналирование всех вызовов | В `syscalls_log`: имя, аргументы, пользователь, статус | Сверка числа вызовов и записей |
| S4 | Привилегированные вызовы только для admin | `sys_useradd`, `sys_log_view` отказывают роли user | Тест ролей |

### 4.4. Поддерживаемость
| ID | Требование | Метрика | Проверка |
|---|---|---|---|
| M1 | Модульность | Один модуль — одна задача, ≤ 300 строк | `wc -l src/*.py` |
| M2 | Документирование | Docstring у каждого модуля и публичной функции | Ревью кода |
| M3 | Автотесты | Покрытие ключевых сценариев ≥ 70 % | `unittest` |

### 4.5. Ресурсоёмкость
| ID | Требование | Метрика | Проверка |
|---|---|---|---|
| E1 | Только стандартная библиотека Python 3.10+ | 0 внешних зависимостей | Отсутствие `requirements.txt` |
| E2 | Размер файла БД после 1000 вызовов | ≤ 5 МБ | Проверка размера `os.sqlite` |
| E3 | Потребление ОЗУ хост-процессом | ≤ 100 МБ | `tracemalloc` / диспетчер задач |

## 5. Анализ рисков

| № | Риск | Вероятность / влияние | Стратегия минимизации |
|---|---|---|---|
| 1 | Нехватка времени | Высокая / высокое | Приоритеты: ядро и БД → ФС и оболочка → доп. функции |
| 2 | Блокировки SQLite при частых обращениях | Средняя / среднее | Единственное соединение, очередь запросов, короткие транзакции |
| 3 | Сложность отладки системных вызовов | Средняя / среднее | Сквозное логирование (БД + файл) с параметрами и результатом |
| 4 | Пропущенная обработка ошибок | Высокая / высокое | Чек-лист: `try/except` в каждом модуле; тесты ошибочных сценариев |
| 5 | Потеря целостного представления о проекте | Средняя / среднее | Актуальная документация, сверка перед каждым коммитом |
| 6 | Разрастание модулей (>300 строк) | Средняя / низкое | Раннее разбиение (fs, proc, mem, auth, scheduler) |
| 7 | Слабые учебные пароли по умолчанию | Низкая / низкое | Смена паролей при первом входе; в документации отмечено, что это учебные данные |
| 8 | Путаница «реализовано / имитировано» | Средняя / среднее | Раздел 2 документа как источник истины |

## 6. Описание прототипа

| Модуль | Назначение |
|---|---|
| `src/config.py` | Пути, версия ОС, пороги NFR |
| `src/logger.py` | Файловый журнал `logs/os.log` |
| `src/db.py` | Единственное соединение, создание 4 таблиц, начальные пользователи (пароли — SHA-256) |
| `src/syscalls.py` | Декоратор `@syscall` (автологирование), `sys_echo`, `sys_get_users` |
| `src/kernel.py` | Диспетчер: перехват исключений, замер времени по NFR P1 |
| `src/shell.py` | Баннер, команды `help`, `echo`, `users`, `exit` |

**Проверка:**
1. `python src/db.py` — появился `db/os.sqlite` с таблицами `users`, `processes`, `files`, `syscalls_log`.
2. `python -m src.shell` — баннер, `help`, `echo Привет`, `users`, `exit`.
3. В SQLite Viewer в `syscalls_log` есть записи `sys_echo` и `sys_get_users` со статусом `ok`.
4. `python -m unittest discover -s tests -t .` — тесты проходят.

## 7. Словарь терминов

| Термин | Определение |
|---|---|
| Операционная система | Программный комплекс, управляющий ресурсами вычислительной системы и предоставляющий программам единый интерфейс к ним |
| Ядро | Постоянно находящаяся в памяти часть ОС, управляющая всеми ресурсами и обрабатывающая запросы программ |
| Пространство ядра (Kernel Space) | Защищённая область памяти, доступная только коду ядра |
| Пространство пользователя (User Space) | Область, где работают прикладные программы и оболочка без прямого доступа к ресурсам |
| Системный вызов | Формализованный интерфейс, через который программа запрашивает у ядра привилегированную операцию |
| Процесс | Программа в момент выполнения со своим состоянием: регистры, память, открытые файлы |
| Поток | Лёгкая единица выполнения внутри процесса, разделяющая с другими потоками его адресное пространство |
| Дескриптор | Числовой идентификатор открытого файла или ресурса, через который выполняются операции |
| Планировщик | Модуль ядра, выбирающий, какой процесс получит процессор |
| Виртуальная память | Механизм, при котором адреса процесса транслируются ядром в физические, создавая иллюзию отдельной памяти |
| Страница | Блок фиксированного размера — минимальная единица выделения памяти |
| Хэширование | Необратимое преобразование данных в строку фиксированной длины (например, SHA-256) |
| Аутентификация | Проверка подлинности пользователя |
| Авторизация | Определение действий, разрешённых пользователю |
| Монолитное ядро | Архитектура, где все подсистемы работают в едином адресном пространстве ядра |
| Драйвер | Программа, обеспечивающая взаимодействие ядра с устройством |

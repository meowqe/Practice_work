# Занятие 1. Границы операционной системы и нефункциональные требования

## 1. Название и концепция

**MyOS** — учебная операционная система с **монолитным ядром**, написанная на Python 3.10+.
Все подсистемы ядра (процессы, память, файловая система, защита) работают в едином
адресном пространстве. Физическим носителем служит база данных **SQLite**
(`db/os.sqlite`): она заменяет диск и хранит файлы, процессы, пользователей и журнал
системных вызовов. Пользователь работает через командную оболочку (User Space),
которая обращается к ядру (Kernel Space) только через системные вызовы.

Идея проекта: показать на небольшом, но работающем коде, как ОС управляет *ресурсами*
(процессы, память, файлы), а не бизнес-сущностями.

## 2. Границы системы

### 2.1. Входит в ОС (реализуется)

| Подсистема | Что реализуется |
|---|---|
| Управление процессами | реестр процессов, состояния (new/ready/running/waiting/terminated), планировщик Round Robin |
| Управление памятью | учёт страниц, выделение/освобождение, лимит на процесс |
| Файловая система | файлы и каталоги в таблице `files`, дескрипторы, права по владельцу |
| Защита | аутентификация (логин + SHA-256), роли admin/user, авторизация |
| Журналирование | запись всех системных вызовов в `syscalls_log` |
| Командная оболочка | `help`, `echo`, `users`, `exit` (прототип), далее — команды ФС и процессов |

### 2.2. Не входит в ОС (имитируется или исключено)

| Функция | Обоснование |
|---|---|
| Реальная работа с оборудованием | Python работает поверх ОС хоста, прямой доступ к железу невозможен. |
| Прерывания и драйверы | Требуют знания аппаратуры и кода уровня ядра (C/ассемблер). Таймер, клавиатура, диск, экран заменяются заглушками. |
| Интеграция со службами каталогов (LDAP, AD) | Нет внешней инфраструктуры; пользователи хранятся в локальной таблице `users`. |
| Сетевые протоколы | Отдельная большая подсистема, выходит за рамки отведённого времени. |
| Графический интерфейс | Тема проекта — ядро, а не GUI; достаточно консольной оболочки. |
| Реальная виртуальная память (MMU, подкачка с диска) | Аппаратная функция; имитируется таблицей страниц в памяти Python. |
| Многопроцессорность | Планировщик имитирует квант времени в одном потоке; настоящий параллелизм усложнит отладку. |

## 3. Роли

- **Пользователь (user)** — работает с файлами только в своём каталоге `/home/<login>`.
- **Администратор (admin)** — полные права: управление пользователями, любыми файлами и процессами.
- **Система (system)** — фоновые задачи: планировщик, сборщик освободившейся памяти.

## 4. Сценарии использования

| № | Сценарий | Актор | Системные вызовы | Модули |
|---|---|---|---|---|
| 1 | Вход в систему | user/admin | `sys_login(login, password)` | shell, kernel, auth, db (`users`) |
| 2 | Создание файла | user/admin | `sys_create(path)` → проверка прав → запись в `files` → лог | shell, kernel, fs, db |
| 3 | Чтение файла | user/admin | `sys_open(path)` → `sys_read(fd)` → `sys_close(fd)` | shell, kernel, fs, db |
| 4 | Запись в файл | user/admin | `sys_open(path)` → `sys_write(fd, data)` → `sys_close(fd)` | shell, kernel, fs, db |
| 5 | Запуск процесса | user/admin | `sys_exec(name)` → создание записи в `processes` → `mem_alloc` → постановка в очередь | shell, kernel, process, memory, scheduler, db |
| 6 | Просмотр списка процессов | user/admin | `sys_ps()` | shell, kernel, process, db |
| 7 | Завершение процесса | owner/admin | `sys_kill(pid)` → смена состояния на `terminated` → `mem_free` | shell, kernel, process, memory, db |
| 8 | Выделение памяти | процесс | `sys_alloc(pid, kb)` (при превышении лимита — отказ и запись в журнал) | kernel, memory, db |
| 9 | Просмотр журнала вызовов | admin | `sys_log_view(limit)` | shell, kernel, db (`syscalls_log`) |
| 10 | Завершение работы ОС | admin | `sys_shutdown()` → остановка процессов → закрытие БД | shell, kernel, scheduler, db |

Реализованы в прототипе: `sys_echo`, `sys_get_users`. Остальные вызовы — задел на следующие занятия.

## 5. Нефункциональные требования

### 5.1. Производительность
| ID | Требование | Метрика / проверка |
|---|---|---|
| P-1 | Обработка одного системного вызова ≤ **50 мс** | замер `time.perf_counter()`; превышение помечается `SLOW` в журнале |
| P-2 | Одновременно поддерживается ≥ **10 процессов** | тест: создать 10 процессов, все в состоянии `ready/running` |
| P-3 | Запуск оболочки (включая инициализацию БД) ≤ **1 с** | замер времени до приглашения |
| P-4 | Квант планировщика Round Robin — **100 мс** (условных) | значение в `config.py`, проверка тестом |

### 5.2. Надёжность
| ID | Требование | Метрика / проверка |
|---|---|---|
| R-1 | Исключение в системном вызове не завершает ядро | тест: вызов с ошибкой → в журнале `ERROR`, оболочка продолжает работу |
| R-2 | Превышение лимита памяти (**4096 КБ** на процесс) — отказ с кодом ошибки, процесс остаётся живым | тест `sys_alloc` сверх лимита |
| R-3 | Некорректный процесс переводится в `terminated` с записью в журнал | тест деления на ноль в процессе |
| R-4 | Повторная инициализация БД не уничтожает данные | `CREATE TABLE IF NOT EXISTS`, повторный запуск `db.py` |

### 5.3. Безопасность
| ID | Требование | Метрика / проверка |
|---|---|---|
| S-1 | Пароли хранятся только как **SHA-256** хэш | в `users.password_hash` нет открытых паролей |
| S-2 | 100 % системных вызовов попадают в `syscalls_log` (имя, аргументы, пользователь, статус) | сравнение числа вызовов и записей |
| S-3 | Обычный пользователь не изменяет и не удаляет файлы admin | тест: отказ `PermissionDenied` |
| S-4 | После 3 неудачных попыток входа — блокировка на 30 с | тест `sys_login` |

### 5.4. Поддерживаемость
| ID | Требование | Метрика / проверка |
|---|---|---|
| M-1 | Код разбит на модули с одной ответственностью | отдельные файлы kernel/syscalls/shell/db/config |
| M-2 | Размер модуля ≤ **300 строк** | `wc -l src/*.py` |
| M-3 | Покрытие ключевых функций автотестами (unittest) | `python -m unittest discover tests` проходит |
| M-4 | Каждая публичная функция имеет docstring | выборочная проверка |

### 5.5. Ресурсоёмкость
| ID | Требование | Метрика / проверка |
|---|---|---|
| C-1 | Только стандартная библиотека Python 3.10+ | отсутствие `requirements.txt` с внешними пакетами |
| C-2 | Не требуется сервер СУБД | используется встроенный `sqlite3` |
| C-3 | Размер файла БД после прогона тестов < **5 МБ** | `ls -l db/os.sqlite` |

## 6. Анализ рисков

| № | Риск | Вероятность | Стратегия минимизации |
|---|---|---|---|
| 1 | Нехватка времени | высокая | Приоритеты: ядро + БД → ФС + оболочка → дополнительные функции |
| 2 | Блокировки SQLite при частых обращениях | средняя | Короткие транзакции, один поток, при росте нагрузки — единое соединение и очередь запросов |
| 3 | Сложность отладки системных вызовов | высокая | Сквозное логирование всех вызовов с параметрами и результатом |
| 4 | Пропущенная обработка ошибок | средняя | Декоратор `@syscall` перехватывает исключения; чек-лист по модулям |
| 5 | Потеря целостного представления о проекте | средняя | Вести эту документацию и сверяться с ней перед каждым этапом |
| 6 | Разрастание модулей сверх 300 строк | средняя | Раннее разделение на подмодули (`fs`, `process`, `memory`) |
| 7 | Потеря данных при сбое записи в БД | низкая | Транзакции (`commit` после операции), Git для кода, резервная копия `os.sqlite` |

## 7. Описание прототипа

| Модуль | Назначение | Как проверить |
|---|---|---|
| `src/config.py` | пути и константы (50 мс, 10 процессов, 4096 КБ) | импорт без ошибок |
| `src/db.py` | подключение, создание таблиц `users`, `processes`, `files`, `syscalls_log`, учётные записи по умолчанию | `python src/db.py` → появился `db/os.sqlite` |
| `src/kernel.py` | состояние ядра, автоинициализация БД | запуск оболочки на чистой папке |
| `src/syscalls.py` | `log_syscall`, декоратор `@syscall`, `sys_echo`, `sys_get_users` | `python -m unittest discover tests` |
| `src/shell.py` | баннер, цикл команд `help/echo/users/exit` | `python -m src.shell` |

Проверка логирования: после `echo` и `users` в таблице `syscalls_log` появляются записи
`sys_echo` и `sys_get_users` со статусом `OK`.

Учётные записи по умолчанию: `admin / admin123`, `user / user123` (хранятся как SHA-256).

## 8. Словарь терминов

1. **Операционная система (ОС)** — программный комплекс, управляющий ресурсами вычислительной системы и предоставляющий интерфейс для программ и пользователей.
2. **Ядро** — центральная часть ОС, постоянно находящаяся в памяти и управляющая всеми ресурсами.
3. **Пространство ядра (Kernel Space)** — защищённая область памяти, доступная только коду ядра.
4. **Пространство пользователя (User Space)** — область, где выполняются прикладные программы и оболочка без привилегий.
5. **Системный вызов** — формализованный интерфейс, через который программа запрашивает у ядра привилегированную операцию.
6. **Процесс** — программа в момент выполнения со своим состоянием: регистры, память, открытые файлы.
7. **Поток** — легковесная единица выполнения внутри процесса, разделяющая с другими потоками его адресное пространство.
8. **Дескриптор** — числовой идентификатор открытого файла или ресурса, через который выполняются операции чтения и записи.
9. **Планировщик** — модуль ядра, выбирающий, какой процесс получит процессор.
10. **Виртуальная память** — механизм, при котором процесс работает с виртуальными адресами, а ядро транслирует их в физические.
11. **Хэширование** — необратимое преобразование данных в строку фиксированной длины (например, SHA-256); применяется для хранения паролей.
12. **Монолитное ядро** — архитектура, где все подсистемы ядра работают в одном адресном пространстве (Linux, FreeBSD).
13. **Микроядро** — архитектура с минимальным ядром; остальные службы вынесены в пространство пользователя (Minix, QNX).
14. **Драйвер** — программа, обеспечивающая взаимодействие ядра с аппаратным устройством.
15. **Аутентификация / авторизация** — проверка подлинности пользователя / определение разрешённых ему действий.
